## Notes

- **Task A:** installed `dotenv@17.4.2` prints a randomized console "tip" on load, including one ad for a third-party product ("⌁ auth for agents [www.vestauth.com]") unrelated to dotenv's maintainers' own domain (dotenvx.com). It's inert (just a `console.log` string, no network call, no code execution) but is unwanted marketing noise from a dependency in a data-privacy-sensitive project — worth knowing if it shows up in prod logs. Suppress with `dotenv.config({ quiet: true })` if it becomes annoying.
- **Task B:** Supabase's "Direct connection" host (`db.<ref>.supabase.co`) only resolves via IPv6 — fails with `ENOTFOUND` on networks/hosts without outbound IPv6. Use the **Session pooler** or **Transaction pooler** connection string instead (`aws-0-<region>.pooler.supabase.com`, username becomes `postgres.<project-ref>`), which supports IPv4.
- **Task C:** TASKS.md's Task C list omitted guardians/parents and grades even though MOCK_SCHOOL_DATA.md documents both and the Parent portal view is in MVP scope — added a guardian account per 2 students (siblings) and one grading period of grades per subject so all 4 portal roles (Admin/Teacher/Student/Parent) have real data to view. Idempotency achieved via `TRUNCATE ... RESTART IDENTITY CASCADE` at the top of the seed script rather than per-row upsert logic — simplest option for mock/demo data that's fully regenerated each run.
- **Task E:** Field-level AES-256 encryption (red flag §1) is deferred, not implemented — `ENCRYPTION_KEY` is only a placeholder in `.env.example`. What's actually in place today: bcrypt password hashing (done), audit logging on login (done), Supabase's provider-level encryption at rest (default, not app-controlled), and a standing "never log PII" comment in `backend/src/db.js`. Deciding which columns need application-level encryption and wiring TweetNaCl in is a real design decision, not infrastructure — treat as its own task before Phase 1 ships, not assumed done.
- **Task K prep:** Task B's schema never gave students a login at all — `users.role` only had ADMIN/REGISTRAR/TEACHER/PARENT, and `students` had no `user_id`. Fixed via `db/schema.sql` (added STUDENT role + `students.user_id`) and re-ran migrate+seed. Also made `schema.sql` re-runnable (`DROP TABLE IF EXISTS ... CASCADE` at the top) since it previously errored on a second run against a live DB — fine for now since `seed.js` always fully repopulates, but this needs real migrations (not DROP+CREATE) before any production data exists. Student login: `student.<lrn>@stmichaels.ph` / `Student@<lrn>`.
- **Task N:** `pg` returns `DATE` columns as JS `Date` objects, not strings — a naive `String(value)` in the CSV serializer produced a full JS date string (`"Thu Dec 19 2019 00:00:00 GMT-0500..."`) instead of `2019-12-19`. Fixed in `backend/src/lib/csv.js` by special-casing `instanceof Date` → `toISOString().slice(0, 10)`. Worth checking for anywhere else a DATE/TIMESTAMPTZ column reaches JSON or CSV output.
- **Frontend build:** when adding `students.user_id` to `seed.js`'s row array (inserted at index 4), the guardian-generation code further down still read `studentRows[i][4]` expecting the student's name — it silently picked up the new `user_id` value instead (no crash, just wrong data: guardian name showed "Guardian of USR-STU-000001 family"). Caught by actually reading the rendered parent-view page in the browser, not just checking HTTP status codes. Fixed by updating the index to `[5]`. Lesson: any time a positional array/tuple gains a field, grep for every other place that indexes into it by number.
- **Task O:** CLAUDE.md §3's stack decision named "TweetNaCl.js" for encryption, but §1's red flag literally says "AES-256" — TweetNaCl's `secretbox` is XSalsa20-Poly1305, not AES, so it can't satisfy a literal AES-256 requirement. Went with Node's built-in `crypto` (`aes-256-gcm`) instead of adding TweetNaCl as a dependency. Only `students.date_of_birth` and `guardians.phone` are encrypted — anything used for sort/search/joins (name, LRN, email) is deliberately left plaintext, since encrypting a searched/sorted column needs deterministic encryption, a materially bigger design decision not taken on here.
- **Task P:** Verified the offline queue/cache actually round-trips (not just "no console errors") by faking `navigator.onLine`/`online`/`offline` events and monkey-patching `window.fetch` to reject, via the browser's JS console — then confirmed the queued write really reached Postgres afterward (`SELECT COUNT(*) FROM attendance WHERE date=...`), not just that localStorage got cleared. `vite-plugin-pwa`'s dev-mode service worker logs a harmless "glob pattern doesn't match any files" warning — real app-shell precaching only happens on `npm run build`, not `npm run dev`. Confirmed: `npm run build` precaches 7 entries (306 KiB) with no errors.
- **Phase 3 scope change:** the user redirected mid-session — remove the Parent role entirely (student login is the shared family login in practice for this school), and add a tuition/SOA feature (manual payment ledger, no payment gateway) plus a grade-promotion/re-enrollment workflow ending in a printable Certificate of Matriculation. None of this was in CLAUDE.md's original MVP list (§0/§2) — flagged here rather than silently treated as always-in-scope.
- **Task V/W bug:** `accounts.js`'s `POST /students/:id/payments` originally hardcoded `CURRENT_SCHOOL_YEAR` — fine for Task V alone, but broke re-enrollment (Task W), where a payment needs to land against the *next* school year's assessment while the student is still in the current one. Fixed by accepting an optional `school_year` in the request body/query (defaults to current). Lesson: a "current year" assumption baked into an endpoint will bite the next feature that needs a different year — worth asking "which year?" explicitly rather than defaulting silently.
- **Task Q limitations (real ones, not just theoretical):** the status page's uptime history is an in-memory array in the Node process — it resets to empty on every server restart/redeploy, so "uptime %" only ever reflects time since the process last started, not real historical uptime. Backup files land on local disk (`backend/backups/`, gitignored) — fine for this dev machine, but not actual disaster recovery: a disk failure here loses the backups too. Both would need real infrastructure to fully satisfy CLAUDE.md §1.5 (persistent history store, e.g. a DB table or external monitoring; off-machine backup storage, e.g. S3/DO Spaces) — flagged, not solved. DB failover replica and zero-downtime deploy remain hosting-tier decisions, unchanged from the earlier note.
- **`scripts/restore.js` (genuinely tested, not just written):** first attempt failed — `audit_logs`/`backups` hold FKs into `users`/`schools` but aren't part of the backup dump, so deleting `users` mid-restore hit a FK violation. Fixing that surfaced a second, subtler problem: with the app server still running, a *concurrent* audit_log write from another session landed between the restore transaction's `DELETE FROM audit_logs` and its later `DELETE FROM users` — under READ COMMITTED isolation that new row was visible to the later statement, causing the same FK error again. Real fix: **stop the app before restoring** (also just correct disaster-recovery practice, not a workaround). Verified for real: deleted 2 known students + their attendance/grades, ran `npm run restore -- <file>.json`, confirmed those exact students came back. Real gaps this surfaced: restore does row-by-row `INSERT` (not batched like `seed.js`'s `bulkInsert`) — fine at ~4,225 rows, would need batching at real scale; and restore does not bring back `audit_logs`/`backups` history — a restore point-in-time loses the audit trail since backups don't capture it.

- **Task X:** created `frontend/src/lib/i18n.js` with a component (`LanguageProvider`) inside it — Vite's `.js` transform doesn't enable JSX parsing (only `.jsx`/`.tsx` do), so every import of it broke the whole app with a 500. Renamed to `i18n.jsx`; fixed immediately. Lesson: any new frontend file that returns JSX needs the `.jsx` extension, even a "just a hook/context" file, not just page/component files.
- **Task X:** `users.notify_email`/`notify_sms` are stored preferences only — no email or SMS provider is integrated, so toggling them doesn't actually cause any message to be sent. Real delivery (e.g. a monthly SMS summary, mentioned in MOCK_SCHOOL_DATA.md) would need an actual provider (e.g. Semaphore/Twilio for PH SMS) wired up as its own task.
- **Task X:** the Tagalog translation covers navigation, login, and the Settings modal only — deliberately not every page's full content (table headers, form labels inside Accounts/Enrollment/etc.). Untranslated strings just render in English. Full-app translation would be a much larger, more mechanical task than "add a toggle."
- **Task Y:** in `getStudentAccount()`, rewriting the return object to add `grade_level`/`section`/`adviser_name` used the shorthand property `fee_items` — but the query result was destructured as `{ rows: feeItems }` (camelCase), so `fee_items` referred to a variable that never existed. Node doesn't catch this at parse time; it only throws (`ReferenceError: fee_items is not defined`) when the function actually runs, which happens on every single account lookup — caught immediately by curling the endpoint (500), not by reading the diff. Lesson: shorthand object properties (`{ fee_items, payments }`) silently assume an exact-name variable is in scope; renaming or restructuring a destructure one line above breaks them with no visual cue in the diff.
- **Task Y:** grade and section were never missing from the schema — `classes.grade_level`/`classes.section` existed since Task B, reachable from any student via `class_id`. The "add grade & section" ask was really "expose an existing relationship," not "add a column." Worth checking whether requested metadata already exists via a join before reaching for a migration.
